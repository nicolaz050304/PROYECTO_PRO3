## ⚙️ OPTIMIZACIÓN DE RENDIMIENTO (hacer al FINAL, con todos los REST listos)
- HIKARI (pool de conexiones): cambiar DBManager.getConnection() de DriverManager.getConnection()
  (abre conexión NUEVA cada vez) a un pool HikariCP. El endpoint de Reserva abre ~13 conexiones por
  petición (1 + lookups en el mapper) -> ~8s de latencia. El pool baja a <1s. Toca SOLO el DBManager
  (dependencia al pom + getConnection del pool); los DAO NO cambian; beneficia a TODOS los servicios.
  Hacerlo con commit de respaldo y probar sin fugas de conexión.
- REDIS (caché en memoria) — sugerido por el profesor. Va DESPUÉS de Hikari. Cachear los lookups
  repetidos de Reserva (nombres de alojamiento/anfitrión) y el listado de alojamientos -> de ~8s a ms.
  Infraestructura aparte: instalar/correr Redis (en Windows vía Docker o WSL) + librería Java
  (Jedis/Lettuce) + lógica "busca en Redis, si no MySQL y cachea". Orden: 1) Hikari, 2) Redis.
  Confirmar con el profe si es obligatorio u opcional.
- Para demos mientras tanto: "calentar" el servidor (abrir la app y entrar a Mis Reservas una vez antes
  de presentar) + timeout del frontend ya en 20s.
- NO hacer (sobre-ingeniería para este proyecto): balanceador de carga, microservicios, colas de
  mensajes, CQRS. El problema de escala que resuelven no existe aquí.
